# Mr.Comic — Аудит кода и конкурентный анализ

**Дата:** 2026-07-07
**Метод:** статический аудит (Read/Grep) по всем 16 модулям, 7 параллельных аудит-агентов + конкурентный анализ. socraticode/семантический индекс недоступен (нет Docker) — использован детерминированный grep/read.
**Область:** весь `android/` + сравнение с Android-ридерами.
**Правки кода не вносились** — это read-only аудит.

## Классы уверенности (по Phase 6 SKILL.md)
- **VERIFIED** — подтверждено чтением исходников (указан `file:line`).
- **INFERRED** — следует из кода, но нет запускаемой проверки (нужен эмулятор/сэмпл-файл).
- Тесты не запускались (аудит статический) — поэтому ни один пункт не помечен как проверенный исполнением. Где нужен ранинг — отмечено.

## 0. Резюме для решения

**Что работает:** графические форматы (CBZ/CBR/CB7/CBT, изображения, PDF/DJVU растр) открываются и читаются — подтверждено пользователем и кодом роутинга контейнеров (`ReaderContentPolicy.kt:17-41`, инвариант «reflowable не идёт через raster» соблюдён).

**Два самых опасных дефекта (P0):**
1. **DATA-LOSS при апгрейде** — entity `Comic` содержит колонки без миграций; Room упадёт на валидации схемы, сработает `fallbackToDestructiveMigration(dropAllTables=true)` → вся библиотека и прогресс стираются молча.
2. **Утечки WebView и TextToSpeech** в ридере — не уничтожаются при выходе; TTS/MediaSession/foreground-service живут на весь процесс.

**Приоритет пользователя:** ускорить открытие **текстовых форматов** — см. раздел 7. Открытие идёт на `Dispatchers.IO` (не морозит UI), но пользователь ждёт первую страницу из-за полного парса + сериализации кэша через `runBlocking`.

### P0-1 · DATA-LOSS · Схема Room без миграций → уничтожение библиотеки
- **Где:** `core-model/.../Comic.kt:29-33` (+ `readingProgress`, `currentPage`, `isBookmarked` и др.) vs `core-data/.../AppDatabaseMigrations.kt` (единственный `ALTER TABLE comics` — `libraryShelf`, стр. 96) + `AppDatabase.kt:22` (`version=8`).
- **Сценарий:** у пользователя с ранее установленной БД колонки `readerLocator*` и др. в таблице `comics` отсутствуют. Миграции 6→7, 7→8 таблицу `comics` не трогают → Room `TableInfo`-валидация падает `IllegalStateException` при открытии → срабатывает `fallbackToDestructiveMigration(dropAllTables=true)` (`DatabaseModule.kt:37`) → дропаются `comics`, `saved_quotes`, `audiobooks`, `text_highlights`, `translation_cache`. Вся библиотека, прогресс, цитаты, выделения теряются без предупреждения.
- **Уверенность:** VERIFIED (лично сверено: entity, версия, отсутствие ALTER для этих колонок).
- **Фикс:** добавить `MIGRATION_8_9` с `ALTER TABLE comics ADD COLUMN ...` для всех недостающих колонок; убрать `dropAllTables=true` на основной БД (заменить на явный отказ/бэкап). Обязателен схема-тест миграции (`MigrationTestHelper`).

### P0-2 · RESOURCE-LEAK · WebView не уничтожается
- **Где:** `feature-reader/.../ReaderScreen.kt:3132` — `AndroidView(factory={ ReaderWebView(ctx) })` без `onRelease`/`DisposableEffect{ webView.destroy() }` (destroy есть только в `onRenderProcessGone:3453`). Аналогично `components/WebtoonView.kt:184` — WebView на каждую HTML-страницу вебтуна без destroy при рециклинге.
- **Плюс:** `ReaderScreen.kt:3199` `addJavascriptInterface(..., "_NativeReader")` захватывает `context` (Activity) → удержание Activity/ViewModel через JS-мост, пока WebView жив.
- **Сценарий:** каждый вход в ридер/прокрутка вебтуна накапливает WebView + renderer процессы. Рост памяти, возможные OOM при длительной сессии.
- **Уверенность:** VERIFIED.
- **Фикс:** `DisposableEffect` с `webView.destroy()` и `removeJavascriptInterface` в `onRelease`.

### P0-3 · RESOURCE-LEAK · TextToSpeech / MediaSession не освобождаются
- **Где:** `ReaderScreen.kt:3675` — `ttsController = remember { ReaderTextToSpeechControllerStore.get(context) }` (процесс-синглтон), `release()` (`ReaderTextToSpeechController.kt:327-334`) не вызывается ни в одном `onDispose`.
- **Сценарий:** `TextToSpeech.shutdown()` не вызывается никогда; `MediaSession`, `BroadcastReceiver`, foreground-service переживают выход из ридера. Утечка на весь процесс, лишний расход батареи.
- **Уверенность:** VERIFIED.
- **Фикс:** `DisposableEffect` → `ttsController.release()`; при вводе dispose проверить P1-9 (вызовы после release).

## 2. P1 — Высокий (ANR / потеря функций / контрактные баги)

### P1-1 · LOGIC · Комикс с `readme.txt` классифицируется как книга — теряются все страницы
- **Где:** `engine-formats/.../ArchiveFormatSupport.kt:85` (`txt`/`html`/`md` в `primaryFormats`) + `isDominantBookEntry:99` (`primaryBookCount==1 → true`) + `classify:57-64`.
- **Сценарий:** архив `[001.jpg…050.jpg, readme.txt]` → `classify()` возвращает `SINGLE_BOOK` → рендерится `readme.txt`, все страницы комикса отбрасываются. Нарушение инварианта «archive classification before rendering».
- **Уверенность:** VERIFIED (лично сверено).
- **Фикс:** не считать `txt/html/md` доминантной книгой при наличии ≥2 image-entries; учитывать долю изображений.

### P1-2 · ANR · Бесконечный цикл / креш на TAR-записи
- **Где:** `engine-formats/.../ArchiveDelegatingFormatReader.kt:332,429` — `copyTo(bufferSize = entry.size.toInt().coerceAtMost(8192))`.
- **Сценарий:** запись с `size==0` → `ByteArray(0)`, `read()` возвращает 0 (не -1) вечно → зависание потока (ANR). Запись >2 ГБ → `toInt()` отрицательный → `NegativeArraySizeException`.
- **Уверенность:** VERIFIED.
- **Фикс:** `bufferSize = entry.size.toInt().coerceIn(1, 8192)` с дефолтом при size≤0.

### P1-3 · ANR · Три `runBlocking` в `onCleared()` ридера
- **Где:** `ReaderViewModel.kt:3947` (`flushPendingProgressSave`), `:3960` (`closeActiveBookSession`), `:3983` (`recordSessionMinutes`).
- **Сценарий:** закрытие ридера блокирует главный поток тремя IO/DataStore-операциями подряд → фриз анимации закрытия / ANR на медленном диске.
- **Уверенность:** VERIFIED.
- **Фикс:** сохранять прогресс заранее (по ходу чтения) + `GlobalScope`/`applicationScope`-launch для финальной записи, либо WorkManager. `onCleared` не должен блокировать.

### P1-4 · ANR · Блокирующий IO аудиокниг на главном потоке
- **Где:** `feature-library/.../LibraryViewModel.kt:1039` (`repairMissingAudiobookCovers` на КАЖДУЮ эмиссию collect, Main), `:1088` (`addAudiobookFromFolder` — рекурсивный `DocumentFile.listFiles()` без смены диспетчера), `:1069` (`addAudiobookFromUri` — `MediaMetadataRetriever` + копирование файла на Main). `AudiobookPlayerViewModel.kt:119` (`resolveAudiobookCover` на Main при открытии плеера).
- **Сценарий:** открытие/обновление библиотеки и импорт аудиокниг из большого SAF-дерева фризят UI.
- **Уверенность:** VERIFIED.
- **Фикс:** обернуть в `withContext(Dispatchers.IO)`; кэшировать резолв обложек, не гонять на каждую эмиссию.

### P1-5 · LOGIC · Kotlin-remap текстовой пагинации мёртв → неверный счётчик страниц/прогресс
- **Где:** `ReaderContentPolicy.kt:62` (`shouldUseKotlinTextPagePagination=false`), `TextReaderOrchestrator.kt:147-191` (публичный `scheduleTextPagePaginationBuild` не вызывается; VM зовёт private-no-op `ReaderViewModel.kt:3704-3710`).
- **Сценарий:** `isTextPagePaginationReady()` всегда false → навигация оперирует индексом spine-секции, а WebView режет секцию на N экранов. Счётчик страниц = число секций, а не реальных экранов; TOC/переходы приземляются в начало секции, прогресс неточный.
- **Уверенность:** VERIFIED (лично сверено, что паджинатор отключён).
- **Примечание:** это делает ledger-дефекты про `0.56f`/char-оценку (`TextPaginator.kt:120-129`) **латентными** — код мёртв в рантайме. Не тратить усилия на его починку; либо удалить мёртвый путь, либо получать реальный page-count из WebView (`onPagedLayoutPageCountChanged`) как единый источник истины.

### P1-6 · LOGIC · TOC в EPUB ведёт не в ту главу
- **Где:** `feature-reader/.../TextBookSessionBridge.kt:70` — при несовпадении href `locator.pageIndex?.let { return it }` возвращает legacy/глобальный page-index как индекс секции, минуя `mapLegacyPageToSectionIndex` (правильный ремап ниже, стр. 72-78, обходится коротким замыканием).
- **Сценарий:** переход по оглавлению в reflowable EPUB прыгает не в ту главу.
- **Уверенность:** VERIFIED.
- **Фикс:** убрать раннее `return` по pageIndex; всегда ремапить через `mapLegacyPageToSectionIndex`.

### P1-7 · PERF/RACE · Осиротевшие декоды страниц при флинге
- **Где:** `engine-rendering/.../PagePreloader.kt:126,179` — `loadPage()` запускает `scope.async(...)` в независимом `scope`, не child от `preloadJob`. `preloadJob.cancel()` отменяет только `await()`, но `Deferred` декодирования доигрывает и делает `putPage`. `decodeSemaphore=Semaphore(2)` (стр. 46): осиротевшие декоды держат пермиты → декод видимой страницы стоит в очереди.
- **Сценарий:** быстрый флинг растрового комикса → накопление устаревших декодов, голодание актуального рендера, лишняя память.
- **Уверенность:** VERIFIED (структура кода), INFERRED (эффект голодания).
- **Фикс:** запускать декоды как child текущего preload-job; отменять при смене окна.

### P1-8 · LOGIC · Мини-плеер аудиокниги нельзя закрыть
- **Где:** `feature-library/.../MiniAudiobookPlayer.kt:159` — кнопка «стоп/X» вызывает лишь `pause()`+`saveProgress()`, не сбрасывает `audiobook`. `AnimatedVisibility(visible = audiobook != null)` → полоса не скрывается. Метода очистки нет.
- **Уверенность:** VERIFIED.
- **Фикс:** добавить `clearAudiobook()` в VM, вызвать из кнопки.

### P1-9 · CRASH · Дубли format-каталога дрейфнули от единого источника
- **Где:** `app/.../navigation/AppNavigation.kt:498-528` (хардкод MIME для file picker — нет 7z/tar/fb2/comicbook+zip) + `app/.../MainActivity.kt:537-561` (`resolveIncomingExtension` дублирует `ReaderFormatCatalog.detectByMimeType`, нет AZW3/FB2). Есть готовые `ReaderFormatCatalog.readerOpenDocumentMimeTypes` и `IncomingOpenFormatPolicy`, но они не используются.
- **Сценарий:** ряд поддерживаемых форматов не выбирается из пикера / входной content-URI получает пустое расширение → книга не открывается. Нарушение инварианта «format catalog single-sourced».
- **Уверенность:** VERIFIED.
- **Фикс:** заменить хардкод на обращение к `ReaderFormatCatalog`/`IncomingOpenFormatPolicy`.

## 4. Нарушения архитектурных инвариантов

1. **Engine boundary (инвариант №3) нарушен массово.** `feature-reader` напрямую импортирует реализации `engine.formats.*` и `engine.rendering.preload.PagePreloader` в продакшн-коде: `ReaderViewModel.kt:67-78`, `TextBookSessionBridge.kt:7`, `TextPagePaginationController.kt:3-7`, `TextReaderSession.kt:3`, `TextReaderController/Orchestrator.kt` и др. Также `core-domain/GetComicPagesUseCase.kt`. Причина: `engine-api` не имеет surface для постраничного рендера/пагинации, поэтому фичи вынуждены обходить контракт. **VERIFIED.**
   - *Замечание:* строгий grep-инвариант в SKILL.md не ловит это, т.к. реальные контракты живут в `engine-formats.base`, а не в `engine-api`. Возможно, стоит либо расширить `engine-api`, либо признать `engine-formats.base` частью контрактного слоя.
2. **Format catalog single-sourced (инвариант №4)** — нарушен в `app/` (P1-9).

## 7. Латентность открытия текстовых форматов (приоритет пользователя)

**Диагноз (Phase 3, предварительный — без ранинга):** открытие текстовой книги выполняется на `Dispatchers.IO` (`ReaderViewModel.kt:642`), поэтому UI **не морозится** — но пользователь ждёт первую страницу, т.к. до её показа выполняется вся тяжёлая работа последовательно.

**Точки задержки при первом открытии EPUB:**
1. **Полный парс EPUB целиком** до показа первой страницы — кэш манифеста/структуры при первом открытии пуст (`loadManifestFromCache`/`loadParsedFromCache` → null).
2. **JSON-сериализация всего манифеста и структуры** в Room-кэш (`storeManifestInCache:1365`, `storeParsedInCache:1405`) на большой книге заметна.
3. **`runBlocking` внутри движка** (`EpubFormatReader.kt:1353,1373,1394,1413`) сериализует чтение/запись кэша, не давая шагам идти параллельно.
4. Первичная пагинация WebView по всему документу до отрисовки.

**Кандидаты на ускорение (для отдельной задачи, требуют Phase 3-верификации профилированием):**
- **Ленивая первая секция:** отрисовывать первую spine-секцию сразу, парсить/пагинировать остальное в фоне после показа. Это самый большой рычаг для perceived latency.
- **Запись кэша не блокируя открытие:** `storeManifestInCache/storeParsedInCache` вынести в fire-and-forget корутину (`applicationScope.launch(IO)`) вместо `runBlocking` в пути открытия — открытие не должно ждать записи кэша.
- **Инкрементальный/потоковый парс** больших EPUB вместо «всё в память + сериализация».
- **Прогрев кэша** при импорте в библиотеку (фоново), чтобы первое открытие уже было тёплым.
- Проверить, не гоняется ли пагинация дважды (мёртвый Kotlin-путь P1-5 + WebuView) — устранить мёртвый путь, чтобы не тратить CPU.

**Как измерить (обязательно перед правкой):** добавить временные метки в путь `openComic` → `reader.open` → первая `getHtmlPage` → первый `onPagedLayoutPageCountChanged`; открыть большой EPUB (>5 МБ) и малый, замерить холодное/тёплое открытие. Это даст точную дельту и подтвердит гипотезу до изменений.
